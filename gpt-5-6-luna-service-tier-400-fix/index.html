gpt-5.6-luna 报 Invalid service_tier argument：先查项目允许的服务层级

如果调用 gpt-5.6-luna 时返回 400，信息是「Invalid service_tier argument: The requested service tier is not allowed for this project.」，原因是这次请求实际要走的服务层级被项目或组织设置禁用了，跟提示词和模型名没有关系。OpenAI 在 2026-10-21 的更新日志中加入了按项目限制服务层级的设置。本页根据官方错误码文档、Fast mode 和 Flex 指南，说明怎么判断、怎么改，以及改完怎么验证。

这条 400 报错的原文和含义是什么？

官方错误码文档列出的标题是「400 - Invalid service_tier argument」，返回的是 invalid_request_error，error.param 为 service_tier，信息为「The requested service tier is not allowed for this project.」。文档给出的原因是：请求指定的层级，或者系统最终解析出来的层级，不在该项目允许的范围内。

这项限制来自 2026-10-21 的更新：OpenAI 允许在 Platform 设置里选择项目可以使用哪些服务层级，组织层面也可以统一限制。所以同一段代码，在一个项目里正常，换到另一个项目、或者管理员改过设置之后，就可能开始报这个 400。

官方资料：更新日志 https://developers.openai.com/api/docs/changelog ，错误码文档 https://developers.openai.com/api/docs/guides/error-codes 。

gpt-5.6-luna 有哪些服务层级，和 service_tier 的取值怎么对应？

OpenAI 官方价格页中，gpt-5.6-luna 在 Standard、Batch、Flex 和 Fast 下都列有价格；Ultrafast 表里没有这个模型。各层级的单价不同，具体以官网价格页为准。gpt-5.6-luna 的模型页同时列出它支持 Chat Completions、Responses 和 Batch 接口。

请求里的 service_tier 和这些层级的对应关系：default 是标准处理；flex 是 Flex 处理；fast 和 priority 是 Fast mode（Priority processing 在 2026-07-30 改名为 Fast mode，官方说明对支持的模型，把 service_tier 设为 priority 和设为 fast 效果相同）；auto 或不写 service_tier 时，使用项目的默认层级。

错误码文档说明，项目限制作用于 default、flex 和 priority 三个层级，fast 按 priority 判断。Scale Tier 不在这项项目策略之内。

没写 service_tier 为什么也会报这个错？

这种情况容易被忽略。错误码文档明确写到：不写 service_tier 或设为 auto 的请求，如果最终解析出来的层级被禁用，也会返回这个错误。

常见的组合是：项目在 Settings → General 中把 Project Service Tier 设成了 Fast（Fast mode 指南说明，这样设置后，没有指定 service_tier 的请求默认走 Fast mode），而项目或组织的允许列表里又没有 priority。这时代码里一个 service_tier 都没写，请求也会被拒。

所以排查时不能只搜代码里有没有 service_tier，还要看项目的默认层级设置。

按什么顺序排查和修复？

第一步，确认报错的是哪个项目。记下这次请求用的 API Key 属于哪个项目，同时保存完整响应体，确认 error.param 是 service_tier。

第二步，查看允许的层级。官方要求同时检查项目设置和组织设置里允许的服务层级；项目不能启用组织已经禁止的层级。如果组织层面禁用了 priority，只改项目设置是没有用的，需要组织管理员处理。

第三步，修改请求或设置，二选一。一是把请求里的 service_tier 改成项目允许的层级，例如项目只允许 default，就去掉 flex 或 fast；二是请求本来用的是 auto 或不写，就按官方建议修改项目设置，让解析出来的层级在允许范围内，比如把项目默认层级改回允许的层级，或者把该层级加入允许列表。

用 flex 跑 gpt-5.6-luna 时还要注意什么？

Flex 指南说明：Flex 处理用于 Responses 或 Chat Completions 请求，费用更低，代价是响应更慢，偶尔会资源不足；适合模型评测、数据补全、异步任务等非生产或低优先级工作。Flex 目前是 beta，可用模型以价格页为准，价格页的 Flex 一栏列有 gpt-5.6-luna。

Flex 资源不足时返回 429 Resource Unavailable，这种情况官方说明不计费。这个 429 表示资源暂时不足，和上面项目权限导致的 400 不是同一个问题。官方给了两种处理办法：能接受延迟就用指数退避重试；更看重请求能完成、可以接受偶尔多付费用，就回退到标准处理：在重试请求里把 service_tier 设为 auto 或去掉该参数（这时实际使用的是项目默认层级）。注意：如果项目默认层级本身被禁用，这一步又会触发 400。

Flex 响应较慢，官方提示 SDK 默认超时是 10 分钟，长提示或复杂任务可能需要调大，示例里把 Python 的 timeout 设为 900 秒。SDK 遇到 408 Request Timeout 会自动重试两次后再抛出异常。

官方资料：https://developers.openai.com/api/docs/guides/flex-processing 。

用 fast 跑 gpt-5.6-luna 时还要注意什么？

开 Fast mode 可以在单个请求里写 service_tier 为 fast，也可以把项目默认层级设为 Fast。Fast mode 指南没有逐个列出支持的模型，只说完整列表以价格页为准，价格页的 Fast 一栏列有 gpt-5.6-luna。指南只给出了 gpt-5.6-sol 的提速倍数，gpt-5.6-luna 实际能快多少，官方没有写。

同一模型的标准处理和 Fast mode 共用一套限流额度。流量增长过快时，系统可能把部分 Fast 请求降回标准速度并按标准价计费，此时响应里的 service_tier 为 default。官方的经验值是：输入达到每分钟 100 万 token 后，每 15 分钟增幅不超过 50%。

官方还建议不要在 Fast mode 下跑大型 ETL 或批处理任务。gpt-5.6-luna 本来就定位于成本敏感、大批量的场景，离线批量任务可以考虑 Batch 接口或 Flex，把 Fast 留给对延迟敏感的线上请求。

官方资料：https://developers.openai.com/api/docs/guides/fast-mode 。

改完以后怎么确认层级生效？

第一，用同一个项目的 Key 发一条最小请求，确认返回 200，不再出现 Invalid service_tier argument。

第二，看响应对象里的 service_tier 字段。Fast mode 指南说明：对 GPT-5.6 及更早的模型，请求写 priority 或 fast，响应里都返回 priority，所以 gpt-5.6-luna 的 Fast 请求看到 priority 是正常的；如果看到 default，说明请求被降级为标准处理，或者走的就是标准层级。

第三，在用量面板里按 service tier 分组，核对各层级的用量是否符合预期。旧模型的 Fast 用量在面板里同样显示为 priority。

第四，用 flex 的任务要单独统计 429 Resource Unavailable 的次数和重试结果，确认退避或回退逻辑能让任务最终完成。

通过中转站调用 gpt-5.6-luna，还会遇到这个报错吗？

上面的项目设置和允许列表都是 OpenAI 官方账号里的设置。通过中转站调用时，请求转发到哪个上游项目、service_tier 会不会原样传过去、按哪个层级计费，都由平台的配置决定，本页无法保证跟官方直连一致。

如果通过中转调用时收到含 service_tier 的报错，先去掉 service_tier 参数，用默认层级发一条最小请求；如果仍然失败，把完整响应体和请求时间交给平台核对。需要固定使用某个层级时，先确认平台是否支持、按什么价格计费，价格以官网价格页和平台显示为准。
